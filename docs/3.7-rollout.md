# step3.7 롤링 업데이트 · 롤백 · 자동 복구

평가 기준 「배포와 운영 — 롤링 업데이트 · 롤백, Pod 삭제 후 자동 복구」.
수업 Kubernetes Core 05장(Deployment: 롤링 업데이트 · 롤백 · 자동 복구)을 Bus 에 적용한다.
모든 실습 동안 내 PC(WSL)에서 `http://<worker1>:30080/api/favorites` 로 0.2초마다 요청을 보내 **실패 수**를 센다.

| 실습 | 하는 것 | 볼 것 |
|---|---|---|
| 롤링 업데이트 | `app-deployment.yaml` 에 `enableServiceLinks: false` 추가 → apply (revision 2) | 새 ReplicaSet 이 1개씩 늘고 옛 ReplicaSet 이 1개씩 줄어듦 (maxSurge 1 · maxUnavailable 0), 실패 수 |
| 잘못된 업데이트 | 없는 이미지 태그로 `kubectl set image` | 새 Pod ImagePullBackOff, 옛 Pod 2개는 그대로 → 실패 0 |
| 롤백 | `kubectl rollout undo` | 이전 ReplicaSet 을 다시 키움, history |
| 자동 복구 ① Pod | `kubectl delete pod` | ReplicaSet 이 새 Pod (이름 · IP 바뀜) |
| 자동 복구 ② 컨테이너 | 컨테이너 안 PID 1 종료 | 같은 Pod 에서 kubelet 이 재시작 (RESTARTS +1) |

## revision 2 로 바꾼 것 — enableServiceLinks: false

3.5 에서 컨테이너에 `DB_PORT_3306_TCP` · `DB_SERVICE_HOST` 등 넣지 않은 변수가 보였다.
kubelet 이 같은 namespace 의 Service 마다 Docker link 형식 변수를 자동으로 넣기 때문이다(기본 켜짐).
Service 이름이 `db` 라서 `DB_PORT=tcp://<ClusterIP>:3306` 도 들어간다. 지금은 ConfigMap 의 `DB_PORT=3306` 이 우선해 문제가 없지만,
ConfigMap 에서 빠지면 앱이 `int("tcp://…")` 로 시작에 실패한다. 서비스는 CoreDNS 이름으로 찾으므로 이 변수들은 필요 없다 → 끈다.
