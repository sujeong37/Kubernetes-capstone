# step3.12 Kustomize · Helm

3.4~3.11 에서 매니페스트를 파일마다 `kubectl apply -f` 했다. 파일이 17개가 되자 「Git 과 클러스터가 같은가」를 확인할 방법이 없었다.
3.12 는 같은 매니페스트를 Kustomize 로 묶고, 비교를 위해 app · web 을 Helm 차트로도 만든다.

## Kustomize (채택)

| 파일 | 내용 |
|---|---|
| `k8s/step3/kustomization.yaml` | base — 3.4~3.11 매니페스트 17개(오브젝트 22개). Secret 은 넣지 않음(create-secrets.sh) |
| `k8s/overlays/pin-commit/kustomization.yaml` | overlay — base 를 그대로 쓰고 이미지 태그만 `step2.3` → `step2.3-aaa4404`(같은 빌드의 커밋 태그) |

| 명령 | 뜻 |
|---|---|
| `kubectl kustomize k8s/step3` | 합쳐진 YAML (적용하지 않음) |
| `kubectl diff -k k8s/step3` | Git ↔ 클러스터 차이. 없으면 출력 없음 · 종료 코드 0, 있으면 1 |
| `kubectl apply -k k8s/step3` | 한 번에 적용 · 손으로 바꾼 값(drift)을 Git 값으로 되돌림 |
| `kubectl diff -k k8s/overlays/pin-commit` | image 두 줄만 바뀜 |

- 공통 라벨을 넣지 않은 이유: `labels`/`commonLabels` 는 selector 를 바꿔 Deployment 를 다시 만들어야 한다.
- overlay 를 base 폴더 안에 두면 `cycle detected` — 그래서 `k8s/overlays/` 에 둔다.
- `kubectl delete -k k8s/step3` 은 쓰지 않는다 — Namespace bus 까지 지워 PVC(DB 데이터)가 사라진다.

## Helm (비교용 · 설치하지 않음)

`helm/bus` — app · web 의 ConfigMap · Deployment · Service 5개를 템플릿으로. 원본에서 바꾼 곳은 `{{ .Values.… }}` 자리뿐.

| values | 기본값 |
|---|---|
| image.repository / image.tag | sujeong79 / step2.3 |
| cityCode | "25" |
| app.replicas · web.replicas · web.nodePort | 2 · 2 · 30080 |

- `helm template bus helm/bus -n bus | kubectl diff -f -` → 차이 없음 (Claude 검증: 렌더 결과 5개가 원본 YAML 과 객체 단위로 같음).
- `helm install` 은 실패한다: 이미 kubectl 이 만든 리소스에 Helm 소유 라벨(`app.kubernetes.io/managed-by: Helm`)이 없어서 `invalid ownership metadata`. 한 리소스는 한 도구가 관리한다.

## 왜 Kustomize 인가

| | Kustomize | Helm |
|---|---|---|
| 설치 | kubectl 내장 | 별도 바이너리 |
| 원본 | 평범한 YAML 그대로 (3.4~3.11 그대로 재사용) | 템플릿 (`{{ }}`) — 원본이 그대로는 적용 안 됨 |
| 바꾸는 방법 | overlay 에 바꿀 것만 (patch · images) | values 로 템플릿 자리 채움 |
| 상태 | 없음 (클러스터가 곧 상태) | release 기록(Secret) · `helm rollback` |
| 어울리는 곳 | 우리 앱처럼 직접 쓰는 매니페스트 | 남이 만든 소프트웨어 배포 (Envoy Gateway · metrics-server · 4단계 AWS Load Balancer Controller) |
