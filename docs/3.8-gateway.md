# step3.8 Gateway API (Envoy Gateway)

수업 Kubernetes Core 08장 03(Gateway API) · 05(Gallery)의 Envoy Gateway 구성을 Bus 에 적용한다.

| 자원 (`k8s/step3/gateway/`) | 하는 일 |
|---|---|
| Envoy Gateway v1.10.0 (`install.yaml`) | Gateway API CRD + 컨트롤러 (envoy-gateway-system). Kubernetes 1.34 ~ 1.37 지원 |
| GatewayClass `envoy` | 이 클러스터의 Gateway 구현체 = Envoy Gateway |
| EnvoyProxy `proxy` | 프록시 Pod 2개, 앞의 Service 는 **NodePort** (수업은 MetalLB LoadBalancer) |
| Gateway `bus` | 입구 하나, HTTP 80 |
| HTTPRoute `bus` | `/api` → app:8000, `/` → web:8080 |

## 3.6 NodePort 와 다른 점

| | 3.6 web NodePort | 3.8 Gateway |
|---|---|---|
| 경로별 분기 | 없음 (모든 요청이 Nginx 로, /api 는 Nginx 가 다시 app 으로) | Envoy 가 /api → app, / → web (Nginx 한 단계 생략) |
| 규칙의 위치 | 이미지 속 Nginx 설정 | Kubernetes 객체(HTTPRoute) — kubectl 로 보고 바꿈 |
| 역할 분리 | — | 클러스터 운영자(GatewayClass · Gateway) / 앱 팀(HTTPRoute) |
| 이후 | — | 가중치 분할(카나리아) · 헤더 매치 · TLS 를 같은 객체로 |

## 왜 MetalLB 가 아닌가

수업 VM(VirtualBox)은 MetalLB L2 모드가 ARP 로 가상 IP 를 광고한다. AWS VPC 는 ENI 에 할당되지 않은 IP 의 ARP 를 전달하지 않아 L2 모드가 동작하지 않는다.
그래서 Envoy 앞 Service 를 NodePort 로 둔다. 4단계 EKS 에서는 같은 Gateway API 를 AWS Load Balancer Controller(ALB)가 구현한다 (수업 alb.yaml).
