## 설정과 이유

| 환경 변수 (calico-node) | 값 | 이유 |
|---|---|---|
| `CALICO_IPV4POOL_CIDR` | `10.244.0.0/16` | kubeadm `podSubnet` · controller-manager `--cluster-cidr` · kube-proxy `clusterCIDR` 와 같아야 한다. 원본 주석값 192.168.0.0/16은 VPC(192.168.0.0/16) · 노드 대역(192.168.56.0/24)과 겹친다 |
| `IP_AUTODETECTION_METHOD` | `kubernetes-internal-ip` | kubelet이 보고한 노드 IP(.10/.11/.12)를 Calico도 쓴다. EC2는 NIC가 하나라 first-found도 같은 값이지만, 기준을 하나로 맞춘다 |
| `CALICO_IPV4POOL_IPIP` | `Always` | 노드 간 Pod 패킷을 노드 IP로 캡슐화(IP 프로토콜 4). AWS 보안 그룹이 노드끼리 모든 트래픽을 허용하므로 통과, 바깥 헤더가 노드 IP라 EC2 source/dest check를 끄지 않아도 된다 |
| `CALICO_IPV4POOL_VXLAN` | `Never` | 원본 그대로 |

## EC2에서 확인할 것 (수업 VM과 다른 점)

| 항목 | 수업 (VirtualBox) | EC2 예상 | 이유 |
|---|---|---|---|
| 노드 NIC | 2개 (NAT + host-only) → first-found 문제 | 1개 | 문제 자체가 없음, 설정은 유지 |
| tunl0 MTU | 1480 | 8981 | VPC 점보 프레임 9001 − IP-in-IP 헤더 20 (Calico 자동 감지) |
| 스냅샷 | `vagrant snapshot save ch04-done` | 생략, stop/start로 복구 확인 | |

## 운영 관점

- 설치 완료는 반복 조회 대신 `kubectl rollout status ds/calico-node` · `kubectl wait --for=condition=Ready node --all` 로 기다리고 시간을 잰다.
- 가장 먼저 Ready가 된 노드에 CoreDNS 2개가 몰린다 → `kubectl -n kube-system rollout restart deployment coredns` 로 노드에 나눠 놓는다 (한 노드가 죽어도 DNS 유지).
- calico-node는 노드마다 CPU 250m을 요청한다(t3.medium 2 vCPU의 12.5%). 앱 배치 전에 노드별 남은 자원을 확인한다.
- 노드 간 통신 검증: worker1/worker2에 Pod를 하나씩 `nodeName` 으로 고정 → Pod IP ping, `nslookup kubernetes.default`, worker2에서 `tcpdump ip proto 4` 로 캡슐화 패킷 확인.
