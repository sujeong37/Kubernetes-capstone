# step4.0.3 EC2 클러스터에서 ECR 이미지로 검증

3단계 EC2 kubeadm 클러스터(개발 · 테스트)가 4.0.2 에서 올린 ECR 이미지(aaa4404)를 받아 같은 시나리오를 통과하는지 먼저 확인한다. EKS(4.3)에는 여기서 검증한 태그를 그대로 쓴다.

| 실행 | 어디서 | 하는 일 |
|---|---|---|
| `bash infra/step4/node/ecr-pull-test.sh` | cp | 설치 전: worker · cp 모두 ErrImagePull (no basic auth credentials) |
| `bash infra/step4/node/create-node-role.sh` | WSL | 역할 bus-step4-ec2-node-role (AmazonEC2ContainerRegistryReadOnly) → worker1 · worker2 에만, IMDS v2 · 홉 1 |
| `bash infra/step4/node/setup-ecr-pull.sh` | worker1 · worker2 | ecr-credential-provider + CredentialProviderConfig + kubelet 플래그 2개 → kubelet 재시작 |
| `bash infra/step4/node/ecr-pull-test.sh` | cp | 설치 후: worker Running, cp 는 그대로 실패 / Pod 에서 IMDS v1 거절 |
| `bash infra/step4/node/apply-ec2-ecr.sh` | cp | overlay ec2-ecr (이미지만 ECR) 적용 · 롤링 · imageID |

## 왜 이 방식인가
| 방법 | 문제 |
|---|---|
| imagePullSecrets (docker login 토큰을 Secret 으로) | ECR 토큰은 12시간 → 만료마다 Secret 을 다시 만들어야 한다 |
| IAM 사용자 키를 노드에 | 장기 키가 디스크에 남는다 |
| **노드 역할 + ecr-credential-provider** (채택) | kubelet 이 필요할 때 역할로 토큰을 받는다. 키 · Secret 없음. EKS 노드도 같은 원리 (Auto Mode 는 내장) |

## 계정 ID
ECR 주소에 계정 ID 가 들어가므로 overlay 에는 `ACCOUNT_ID` 자리 표시만 두고, cp 에서 IMDS 인스턴스 신원 문서로 읽어 바꿔 넣는다. 화면 출력은 `****1234`.

## IMDS 를 잠그는 이유
노드에 역할이 생기면 Pod 도 IMDS(169.254.169.254)로 그 역할 자격 증명을 꺼낼 수 있다. worker 의 IMDS 를 v2 전용 · 홉 1 로 바꾸면 노드 자신(kubelet)은 쓰고, 한 홉 더 떨어진 Pod 는 닿지 못한다 → 3.11 「앱 Pod 는 권한 0」 유지.
