# step2.4 Docker Compose 사용

step2.0 ~ 2.3은 `docker/up.sh` 가 `docker run` 을 3번 실행하고, 각 컨테이너가 healthy가 될 때까지 직접 만든 대기 함수로 기다렸다. step2.4는 같은 구성을 `compose.yaml` 하나에 **원하는 상태**로 적고 `docker compose up -d --wait` 로 띄운다. 이미지는 step2.3 그대로다.

## 1. compose.yaml

| 항목 | 내용 | docker run 방식에서는 |
|---|---|---|
| `name: bus` | 프로젝트 이름. 컨테이너 `bus-db-1` 등, 네트워크 `bus_default` 를 자동으로 만든다 | `docker network create bus-net` |
| `x-common: &common` → `<<: *common` | 세 서비스가 같이 쓰는 설정(`restart: unless-stopped`)을 한 번만 적는다 (YAML 앵커) | 명령마다 `--restart` |
| db `healthcheck` | `mysqladmin ping`, 3초 간격, 40번 | `--health-cmd ...` |
| app `depends_on: db: condition: service_healthy` | db가 healthy가 된 뒤 app 시작 | `wait_healthy db 120` (직접 만든 함수) |
| web `depends_on: app: condition: service_healthy` | Nginx는 시작할 때 `app` 이름을 찾으므로 app이 먼저 | `wait_healthy app 60` |
| app · web 건강 검사 | 이미지의 `HEALTHCHECK` 를 그대로 쓴다 | 같음 |
| `env_file: docker/env.docker` | 비밀이 아닌 설정 | `--env-file` |
| `${DB_PASSWORD:?...}` | 비밀은 파일에 적지 않고 셸 환경 변수에서. 없으면 안내하고 멈춘다 | `read -rsp` → `-e 이름` |
| `${IMAGE_PREFIX:-}bus-app:${IMAGE_TAG:-step2.3}` | 레지스트리 이미지 · 태그를 바꿔 띄운다 | `IMAGE_PREFIX` · `IMAGE_TAG` |
| `build: ./app/was` | `docker compose build` 로 이미지도 만들 수 있다 | `build.sh` |
| `volumes: db-data: name: bus-db-data, external: true` | 2.0부터 쓰던 볼륨을 그대로 (즐겨찾기 유지). `compose down -v` 로도 지워지지 않는다 | `docker volume create` |
| `--wait` | 모든 서비스가 healthy가 될 때까지 기다린 뒤 끝난다 | 대기 함수 |

`depends_on` 의 다른 조건 `service_completed_successfully` 는 "한 번 실행하고 끝나는 준비 작업"(예: DB 초기화 전용 컨테이너)을 기다릴 때 쓴다. 이 앱은 초기화를 MySQL 이미지의 `initdb.d` 가 하므로 쓰지 않았다.

## 2. 스크립트

| 파일 | 하는 일 |
|---|---|
| `docker/compose-up.sh` | 비밀번호를 화면에 안 보이게 입력 → `docker compose up -d --wait` → `ps` |
| `docker/compose-test.sh` | 시나리오 T1~T9. T7 뒤에 `docker compose down && docker compose up -d --wait` 로 재시작 |

`docker compose ps` · `logs` · `down` 도 `compose.yaml` 을 읽으므로 비밀번호 환경 변수가 있어야 한다(`:?`). 같은 터미널에서 export 해 둔다. `docker compose config` 는 비밀번호를 그대로 출력하므로 `--quiet` · `--services` 로만 쓴다.

## 3. 확인 (Claude 작업 환경, 대체 바탕 이미지)

| 확인 | 결과 |
|---|---|
| 비밀번호 없이 `docker compose up` | `required variable DB_PASSWORD is missing a value` 로 멈춤 |
| `compose-up.sh` | db → app → web 순서로 healthy, 16.8초 |
| `compose-test.sh` | 9 / 9 (down → up 후 즐겨찾기 유지) |
| `docker compose down` | 컨테이너 · 네트워크 삭제, 볼륨 `bus-db-data` 유지 |

## 4. docker 명령 방식과 비교

| 항목 | docker run (`up.sh` · `down.sh`) | Compose (`compose.yaml`) |
|---|---|---|
| 구성 정의 | 셸 스크립트 38줄 (명령 · 순서 · 대기 함수) | YAML 45줄 (원하는 상태만) |
| 실행 순서 · 대기 | 직접 작성 (`wait_healthy`) | `depends_on` 조건 + `--wait` |
| 네트워크 | 직접 생성 | 자동 생성 · 삭제 |
| 상태 · 로그 | `docker ps --filter` · `docker logs app` | `docker compose ps` · `docker compose logs app` |
| 정리 | `down.sh` (이름 지정 삭제) | `docker compose down` |
| 일부만 다시 | 해당 컨테이너 지우고 같은 `docker run` | `docker compose up -d app` (바뀐 것만 다시 만듦) |
| Kubernetes와의 관계 | 명령형 | 선언형 — 3단계 매니페스트와 같은 사고방식 (Service 이름 = 주소, 상태 검사) |
